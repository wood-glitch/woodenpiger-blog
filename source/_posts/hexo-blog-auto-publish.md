## 现在的样子

博客在 owo24.com，Hexo 7.3.0 + Redefine v2.9.0 主题，源码在 GitHub 仓库 wood-glitch/woodenpiger-blog（main 分支），Cloudflare Pages 自动构建、自动上线。写文章的流程是：在 Muse 的博客生产中心里加一个选题，分析、写稿、配图、审核、发布全走流水线，最后由一台免费云机器推送到仓库，Pages 构建完就上线。截至 2026-11-15，近 30 天访问人数 2,614，总访问量 11,264。

这篇把整条链路拆开，分四步讲：安装博客、注册 InstaBox 服务器、在 Muse 上配好提示词、测试找 bug，最后说最终效果。每一步的命令、配置和预期结果都写清楚，照着做就能复现。

> 提示：文中的作者信息（如 GitHub 用户名、仓库名、机器名、域名、密钥名等）请替换成自己的。

## 一、安装博客

### 选型：为什么是这套组合

- Hexo 是静态博客生成器：文章是 Markdown，生成出来是一堆静态 HTML，没有数据库，不用管服务器运维。
- Cloudflare Pages 托管静态站免费，推代码就自动构建，还能直接绑自定义域名，省掉了买服务器、配 Nginx、续证书的活。
- 主题用 Redefine v2.9.0（之前是 Butterfly，2026-11-15 换过来的），够用。
- 发布机用一台免费云机器（InstaBox，4 vCPU / 8 GiB），只做一件事：存一份博客源码，推送到 GitHub。博客本身不跑在这台机器上——免费机最多连续跑 8 小时，闲置 1800 秒还会自动暂停，拿它当生产服务器不靠谱。托管和发布机分开，是这套方案里最重要的一点。

### 1. 装 Node.js 和 Hexo

本地只需要 Node.js（建议 v20 以上）。装好之后：

```bash
npm install -g hexo-cli
hexo init woodenpiger.blog
cd woodenpiger.blog
npm install
```

装完先别急着写文章，跑一下本地预览，确认站能起来：

```bash
hexo server   # 本地预览，默认 http://localhost:4000
hexo generate # 生成静态文件到 public/
```

`hexo server` 能打开页面、`hexo generate` 不报错，这一步就算过了。`hexo generate` 生成的 public/ 就是最后要发布的东西。

### 2. 装 Redefine 主题

去 Redefine 的 GitHub 仓库下载 v2.9.0：[EvanNotFound/hexo-theme-redefine](https://github.com/EvanNotFound/hexo-theme-redefine)，解压后把整个文件夹放进 `themes/redefine`。然后改站点根目录的 `_config.yml`，把主题指过去：

```yaml
theme: redefine
```

主题自己的配置在 `themes/redefine/_config.yml`，改配色、菜单、社交链接都在这里。改完先 `hexo generate` 看有没有报错，没问题再继续。

### 3. 推到 GitHub，接上 Cloudflare Pages

源码推到 GitHub 仓库（比如 `wood-glitch/woodenpiger-blog`，分支 `main`）。然后去 [Cloudflare 控制台](https://dash.cloudflare.com) 建一个 Pages 项目，连上这个仓库，设置如下：

- 生产分支：`main`
- 构建命令：`npm install && npm install -g hexo-cli && hexo generate`
- 输出目录：`public`
- 自动部署：开

推一次代码，Pages 就构建一次，构建完自动上线。自定义域名在 Pages 项目里绑自己的域名（比如 owo24.com，绑完等 DNS 生效）。之前的域名 wood-glitch.com 没做 301 跳转——没人收藏，没必要。

### 4. 容易踩的坑（都是真踩过的）

- **date 只写日期会错位**：有一篇文章 front-matter 只写了 `2026-10-18`，Pages 在 UTC 构建时把地址算成了前一天 `/2026/10/17/`。修法是 date 一律带具体时间，比如 `2026-11-15 17:45:00`，旧地址用 `_redirects` 做 301 保留（这个文件由 `scripts/cloudflare-redirects.js` 生成，不要手改）。
- **文件名带 #UXXXX 转义**：三篇文章的文件名里有 URL 转义字符，`git mv` 改成干净名字，URL 不变。新建文章时文件名直接用干净的拼音或英文 slug。
- **死的部署配置**：`_config.yml` 里残留的 `deploy:` 段和 `.github/workflows/deploy.yml` 都删了，现在部署只靠 Pages，留着它们只会误导人。
- **主题臃肿**：Redefine 主题自带 38 个 `.map` 文件和一个重复的 mermaid.js，删掉，体积直接下来。
- **本地残留**：`_backup/`（35MB）和 `_server.err.log` 只在本地工作目录里，不在 git 里，要手动删。
- **图片太大**：一张 556KB 的照片压到 145KB，封面图一律压到 200KB 以内再进仓库。
- **sitemap 污染**：流量快照文件 `source/data/cloudflare-traffic.json` 要加进 `skip_render`，不然会被收进 sitemap。
- **同步前不 pull 会冲突**：发布机和本地都会往仓库推，任何操作前先 `git pull`。

## 二、注册 InstaBox 服务器

### 1. 注册并创建机器

打开 [instabox.sh](https://instabox.sh)，用 GitHub 登录，进控制台创建一台机器。选 standard 模板：4 vCPU / 8 GiB 内存 / 20 GiB 磁盘，Debian 13。创建时没有地域选项，机器名自己取（比如 agent-browser-wjum）。建好后控制台会给 SSH 登录方式，照着连上去就行——那条 SSH 命令里带你的登录凭证，不要贴到公开地方。

机器的限制要先知道：最多连续跑 8 小时，闲置 1800 秒会自动暂停。出口在美国西海岸（俄勒冈）。它只适合当发布机，不适合当生产服务器。

### 2. 在机器上放一份博客源码

在机器上克隆源码到 `~/blog`，配好 git 身份。然后在 GitHub 仓库 Settings → Deploy keys 里加一个写权限的 key（名字比如 `instabox-blog-src`），公钥放在机器的 `~/.ssh/` 里。发布流程固定四步：

```bash
git pull          # 先拉取，用户自己也会直接往仓库推
# 写文章到 source/_posts/
hexo generate     # 本地验证
git commit + git push 到 main   # Pages 自动构建
```

文章文件在 `source/_posts/`，文件名用干净的拼音或英文 slug，front-matter 的 `date` 必须带具体时间。

### 3. 保活：Worker 每 9 分钟续租（附教程）

免费机有 8 小时上限，闲置还会暂停，不保活的话发布机随时会停。保活用一个 Cloudflare Worker，代码是开源的：[ailg666/instabox-keepalive](https://github.com/ailg666/instabox-keepalive)。它每 9 分钟调一次 InstaBox 的续租接口，租期 900 秒，机器被平台挂起时还会自动调 `/resume` 把它唤醒（停掉的用 `/start` 兜底），再续租。

搭法按这几步来：

1. **新建一个受限 API Key**：去 InstaBox 控制台新建一个 API Key，只给机器读写和快照读权限，不要给完整权限。这个 Key 只用来续租和唤醒，丢了也只能动机器，动不了账号。
2. **建一个 Cloudflare Worker**：在 Cloudflare 控制台新建 Worker，把仓库里的 `worker.js` 代码贴进去，部署。
3. **加两个 Secret**：在 Worker 的设置里加 `INSTABOX_API_KEY`（上一步新建的 Key）和 `TOKEN`（自己编一串随机字符，Worker 校验用，不要用弱口令）。
4. **加租期和定时**：再加一个变量 `INSTABOX_LEASE_TTL=900`（租期 900 秒），然后给 Worker 加一个 Cron 触发器，表达式 `*/9 * * * *`，每 9 分钟跑一次。
5. **验证**：部署后访问 Worker 的 `/status`，返回 `ok:true`、机器状态是 running，就是正常。Worker 的 `/log` 能看最近的续租记录（需要绑 KV，不绑也能用，只是没日志）。

这一步只保发布机不断线，不保博客在线——博客在线靠的是 Pages，跟这台机器没关系。机器停了，最多是推不了文章，线上博客不受影响。

值得注意的是，免费不等于随便用：这台免费机的服务条款明确禁代理，之前在上面装过一次代理，当天就被封了 24 小时。博客这条线从头到尾不碰代理，只推代码。

## 三、在 Muse 上的提示词

写文章本身也有一条流水线，跑在 Muse 的「博客生产中心」空间里，一个页面三个区：选题、配图审核、博客。流程是：

1. **选题**：粘一个 X 链接，或者写一句话想法，状态「待写」。
2. **分析**：链接按免登录规则读（公开接口，不登录、不交账号），想法按 P3 扩展成大纲，写进 `analysis`。
3. **写作**：按 P2 写出完整 Hexo Markdown 草稿，含 front-matter，文末带 AI 声明，状态「已写」。
4. **审稿**：按 P7 对照 P4 九项和风格指南审一版，改完再给用户看。
5. **配图**：按 P6 生成 16:9 封面，存进仓库 `source/images/covers/<slug>.jpg`（200KB 以内），进「待审核」等我看一眼；打回就按意见重画。
6. **发布**：我点发布进「待发布」，门禁三项：草稿已写、配图已通过（或明确不用配图）、P4 自查九项通过。看守任务每 5 分钟跑一轮，门禁通过就推到仓库、验证首页 200、文章 200、sitemap 已更新，状态改「已发布」。

我认为这套流程里最值钱的不是自动化本身，而是门禁：草稿、配图、声明三项缺一不可，拦住了半成品直接上线。门禁是真拦过东西的——缺 AI 声明的草稿直接被拒绝进待发布。

下面是这套流水线用的提示词和规则原文，是现在用的最终版，照抄就能用。直接把整段粘贴给 Muse，让它按这个建一个博客生产中心空间就行：

## P1 文章分析

```
你是一名中文科技博客作者。请免登录阅读以下文章链接，输出结构化分析：
链接：{链接}
我的选题方向：{方向}

输出：
1. 原文核心观点（3-5 条，每条一句话）
2. 最值得写成博客的 2-3 个点（为什么值得写）
3. 原文可商榷或过时的地方（有就写，没有就写"无"）
4. 建议的写作角度（结合我的方向，给 1 个主角度 + 1 个备选）
5. 建议的文章结构（小标题列表）
注意：只基于你实际读到的内容写；没读到的不要编；如果链接读不到，如实说你读到了多少。
```

读链接规则（用户长期规则）：绝不登录任何平台读分享的链接，不索要账号密码 cookie；用免登录渠道（公开元数据、平台访客接口、fxtwitter/vxtwitter 公开 API 等），并如实报告实际取到了多少（全文还是只有摘要）。

深读与事实库：链接里的关键来源（仓库、文档、官方页）最多打开 2-3 个，把核实的事实（版本、命令、链接、价格）带来源和核实日期记进 ~/workspace/blog-pipeline/facts.md；写稿只用事实库和 P1 分析里的事实，不编。事实库是活的，每次核实到新事实就追加一条。

## P2 博客写作

```
根据以下分析写一篇中文科技博客（Hexo Markdown）：
选题方向：{方向}
文章分析：{P1 输出}
博客定位：记录 AI 编程、开发工具与折腾过程；读者是爱折腾的中文技术用户；语气直接、具体、少废话。

要求：
1. 输出 front-matter：title、date（带具体时间，如 2026-11-15 20:00:00）、categories、tags、cover、description
2. 正文用 Markdown，有小标题、代码块（如需）、列表；不要写"首先、其次、综上所述"这类套话
3. 加入你自己的思考：至少一处"我认为/值得注意的是"式判断，并说明理由
4. 不要编造没有来源的数据、价格、版本号；不确定的写"以官方页面为准"
5. 长度：{篇幅，如 1500-2500 字}
6. 文末附上 AI 声明（见下）
7. 如果文章中出现作者本人的标识信息（GitHub 用户名、仓库名、机器名、域名、密钥名、邮箱等），在正文开头显眼处加一段作者信息声明（固定文本见下），提醒读者替换成自己的。
8. 教程类文章要写得详细一点：每一步的操作、命令、配置和预期结果都写清楚，不要只讲思路、跳步骤。
9. 按 ~/workspace/blog-pipeline/style-guide.md 的风格指南写（语气、结构、详略按用户自己的文章来，不要写成通用 AI 腔）。
```

## P3 想法扩展

```
我有一个想法：{用户原话}
请帮我把它扩展成一篇博客选题：
1. 这个想法值得写的理由（1-2 句）
2. 建议的切入角度和文章结构
3. 需要我补充的信息（如果有，列出来问我；没有就直接给大纲）
4. 如果我说"直接写"，就按大纲写出初稿
```

## P4 发布前自查（九项，任何一项答“否”就先改再发布）

```
1. 标题是否准确反映了文章内容，没有标题党？
2. 有没有编造的数据、版本号、价格或链接？草稿里的每一个链接都逐个请求验证过吗（状态码 200/301/302 才算通过，404 直接打回）？链接一律用 [文字](URL) 的形式写，裸 URL 后面不要紧贴中文标点/文字，否则 Markdown 自动链接会把后面的中文吞进 URL 导致 404（2026-11-15 教训：Redefine 和 Cloudflare 控制台两个链接就是这么坏的）。
3. 观点里哪些是原文的、哪些是你自己的思考，分得清吗？
4. 目标读者看完能带走至少一个可操作的结论吗？
5. 分类、标签、封面、摘要都填好了吗？文件名是干净的拼音/英文吗？
6. 日期带具体时间吗（避免之前 xray 文章那种本地和线上地址不一致的问题）？
7. 配图通过审核了吗（或已明确这篇不用配图）？图片已存入仓库、封面链接正确吗？
8. 文末 AI 声明加上了吗？
9. 文章里出现作者本人的标识信息时，开头加了作者信息声明（提醒读者替换成自己的）吗？
```


## P6 配图生成

```
根据以下文章分析生成一张博客封面图的提示词，并直接生成图片：
文章分析：{P1 输出}
选题方向：{方向}
要求：
1. 画面要体现文章的核心主题，不要出现文字（除非主题本身需要）
2. 风格：简洁现代的科技感插画，16:9 横构图，适合做博客封面
3. 避免出现具体品牌 logo、真实人物肖像
4. 输出图片后附上你用的提示词，方便打回重画时调整
```

打回重画时，在 P6 基础上加一句：{用户的打回意见}，重新生成。

## P7 审稿（P2 写完后、交给用户之前，必跑一轮，只改一版）

```
读 P2 草稿全文，对照 P4 九项 + 风格指南（~/workspace/blog-pipeline/style-guide.md），逐条挑问题：
1. 每一步的操作、命令、配置、预期结果是否都写清楚了（教程类重点查这个）
2. 有没有没来源的数据、价格、版本号（有就删掉或标“以官方页面为准”，不要编）
3. 结构是否按用户说的分法（有明确要求时），小标题和顺序是否合理
4. 语气是否像用户的文章（直接、具体、少废话），有没有套话
5. 两条声明是否都在、位置对不对（AI 声明是 div.ai-declaration 在文末；作者信息声明在正文开头）
6. front-matter 是否完整（title、date 带具体时间、categories、tags、cover、description），文件名是不是干净 slug

输出：问题清单（每条写明位置 + 怎么改），然后按清单把草稿改一版，写回 draft 字段。只改一版，不要反复改；改完就停，等用户看。审稿不改事实、不编新内容；发现事实存疑的，记下来告诉用户，不要自己补。
```

## AI 声明（每篇已发布博客文末，固定文本）

渲染形式：用带 `ai-declaration` class 的 div 包住固定文本，荧光边框样式由主题 inject 提供（`themes/redefine/_config.yml` 里 `inject.enable: true`，head 里有一段 `.ai-declaration` 的 `<style>`，青色荧光边 + 浅色文字）。不要只放一段 plain text，那样在深色主题里看不清。

```html
<div class="ai-declaration">AI 声明：本文由 AI 辅助创作，初稿基于公开资料分析生成，经作者审阅、修改后发布；配图由 AI 生成。作者对内容的准确性负责，如有错误，欢迎指正。</div>
```

固定文本（div 里面的句子）：

> AI 声明：本文由 AI 辅助创作，初稿基于公开资料分析生成，经作者审阅、修改后发布；配图由 AI 生成。作者对内容的准确性负责，如有错误，欢迎指正。

> 提示：文中的作者信息（如 GitHub 用户名、仓库名、机器名、域名、密钥名等）请替换成自己的。

## 发布技术规则

- 发布路径：InstaBox 机器 `~/blog` → GitHub `wood-glitch/woodenpiger-blog` main 分支 → Cloudflare Pages 自动构建，域名 owo24.com。
- 机器 SSH：`ssh -p 2222 （按上面第二步，在 InstaBox 控制台拿你自己的 SSH 登录命令）`。任何同步前先 `git pull`（用户也会直接往仓库推）。
- front-matter 的 `date` 必须带具体时间（如 `2026-11-15 20:00:00`），只写日期会在 UTC 构建时把地址算成前一天（2026-11-15 修过 xray 文章这个 bug，旧地址用 `_redirects` 301 保留）。
- 文章文件在 `source/_posts/`，文件名用干净的拼音/英文 slug，绝不用 `#UXXXX` 转义名；`permalink` 与文件名对应，改名不动 URL。
- 封面图存 `source/images/covers/<slug>.jpg`，压缩到 200KB 以内；front-matter `cover` 指向它。

## 四、测试找 bug

流水线搭好先别直接用，先跑一轮端到端测试，找 bug。测试用的是一篇 X 文章（讲 Muse 做动画视频的 18 个免费开源 Skill），流程是：读链接 → 分析 → 写稿 → 配图（故意打回一次，测打回重画）→ 发布 → 线上验证。链接里的 18 个仓库地址逐个点开验证过，都是 200。测试一共找出这些 bug，全修了：

- **配图按内部 id 查条目，查不到**：配图空间按内部 id 查，选题按选题 id 登记，两边对不上，审核按钮点不动。改成按选题 id 查。
- **配图同步不回填标题和提示词**：同步图片时标题和提示词是空的，审核页看不到这张图是给哪篇文章画的。修了同步逻辑。
- **选题库三回丢行**：三回出现选题行莫名消失，查不到是谁删的。加了守则：选题少了不许自己恢复，只有用户明确说才恢复——后来有一次就是用户自己删的，守则正好拦住了误恢复。
- **待发布/草稿箱漏了“已写”**：写好的草稿在两个列表里都不出现，等于丢了。修了列表的筛选条件。
- **想法型选题卡在提问不动**：想法进来先列一堆问题等人回答，自动流程断了。改成自动补背景直接写，只有关键信息实在补不上才停下来问。
- **“在写”但 analysis 和 draft 都空的没人处理**：丢行事故留下的半截状态，没人管。改成按待写处理。
- **发布时 slug 没规定怎么取**：草稿的 slug 和封面文件名可能对不上，封面会 404。规定 slug 取 cover 路径的文件名主干。
- **仓库里没有 source/images/covers/ 目录**：复制封面会失败。发布前先 mkdir -p 建目录。
- **声明竞态**：文章 17:24 发出去了，声明也是 17:24 加的，看守读的是改之前的草稿，线上那版没有声明。发现后直接往仓库补了一次提交，线上验证通过。教训：别在看守正在发布的时候改草稿，等它发完再改。
- **pkill 误杀**：`pkill -f "hexo server"` 把 SSH 会话自己杀了。改成按端口找进程再杀。
- **链接 404（裸 URL 被中文标点吞掉）**：发布后发现两个链接 404——Redefine 仓库和 Cloudflare 控制台的链接，裸 URL 后面紧贴中文标点，Markdown 自动链接把后面的中文吞进了 URL。修法：链接一律用 [文字](URL) 的形式写，这条写进了 P4 和发布规则。
- **发布时没逐个验证链接**：P4 第 2 项写了要验证链接，但发布检查只验证了首页、文章、sitemap 的 200，没逐个点链接，两个 404 就这么漏过去了。修法：发布前用 curl 逐个请求草稿里的每个 URL，200/301/302 才算通过，404 直接打回；这条也写进了 P4 和发布规则。
